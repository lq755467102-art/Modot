# 怎样找到多走的那几轮

[English](engineering-efficiency.en.md)

一次 Agent 任务至少有两个终点。桌面上出现最终答复，是用户结束等待的时间。交付物通过独立评分，是任务做对的证据。我们同时记录这两个结果。一次比较里的延迟、token 和正确率也分别计算。

## 一次真实的反例

同一会话里换了任务，用户只问「帮我找找 bug」。旧版把 97 次历史工具结果带入首包。两个复测把原文移到按权限回读的历史入口。以下数字来自实际发出的请求与提供方回传的用量，已去掉项目、路径、命令正文和用户数据。

| DeepSeek Flash 观测项 | 原运行 | 首次复测 | 再次复测 |
| --- | ---: | ---: | ---: |
| 首包旧回执 | 97 | 0 | 0 |
| 首包输入 token | 177,586 | 11,676 | 11,675 |
| 模型请求 / 工具调用 | 21 / 29 | 30 / 47 | 57 / 110 |
| 总输入 token | 4,133,108 | 2,084,122 | 5,355,307 |
| 输入缓存命中率 | 99.35% | 96.00% | 97.45% |
| 总输出 token（含推理） | 14,548 | 27,148 | 44,982 |
| 估算费用（人民币） | 0.1673 | 0.2320 | 0.4210 |
| 发题到结束，秒 | 505.139 | 157.913 | 267.944 |

首包缩短约 93.4%，57 次那轮末包却增长到 181,011 输入 token。逐次检查后，两次复测主动回读旧操作的次数都是零。57 次那轮有 10 次工具调用在取**本轮**检查结果。重复携带本轮产生的回执，把新增操作的成本逐渐放大。两次复测用同一份文件归档，但原运行有不同权限、依赖和 Git 环境，缓存冷热也有差异。这个开放式查错任务没有全仓缺陷真值，只能核对每条结论是否成立。

## 从一次失败追到负责的环节

1. **先冻结任务和评分。** 保存起点提交、依赖锁、子目录、权限、实际模型和上下文窗口。把评分器放在 Agent 的编辑目录之外。用空改动和一个已知修复各跑一次，再发原题。报告把启动失败、超时、部分通过和全部通过分开。
2. **在模型边界取样。** 对发出的每个请求记录顺序、角色、消息区段、工具定义、首末输入、命中/未命中和完成时间。把原始回执标识与发给模型的投影一一关联。重试也占一次请求。一个已经留档的回执可以完全没有进入这一包。[请求准备](../loop/context_manager.py) · [模型调用观测](../loop/model_observation.py) · [回执裁剪与回读](../loop/tool_spill.py)
3. **把模型结论和环境事实分开核对。** 同一子仓库测试若在固定命令下也找不到依赖，先核对真实工作目录、Node 版本和子进程环境。若工具已返回五个具名用例失败，模型仍说全是环境问题，就给这句判断标上证据不足。若模型只得到「退出 0」，检查回执有没有实际用例数和失败清单。用一份会打印失败却以 0 退出的测试夹具即可分辨两者。
4. **为重复动作找一个具体原因。** 以工具参数、源码版本、工作目录和授权状态给动作分组。相同动作再次执行时，核对最近一个结果在当次请求里是否可见、完整、仍有效。源码或环境已经变化的复跑有价值。记录已过期却仍进入上下文、正在运行却又重复发起、看见明确失败却换种措辞再试，分别对应不同修复点。
5. **用对照决定保留哪项优化。** 一次只改投影、工具或模型中的一项。按同一评分器比较交付率、误报、总用时、整轮费用和缓存命中。保留失败和慢样本。至少覆盖短代码题、长输出、审批中断和换任务后回读，再判断某个截断阈值是否值得推广。

对用户呈现结论时，写清「哪一条命令、多少用例、对应哪版源码」。例如「静态核对覆盖了三个调用方，集成测试未启动」足以让维护者决定下一步。完整工具日志留在本地，公开结果只保留必要的计量、版本和评分。[逐题成绩](benchmarks/modot-engineering-scorecard.md) · [从原始计量重算](../tools/scorecard.py)
